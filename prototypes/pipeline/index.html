The contract is the source of truth

A visual editor and a coding agent both write into one repository. What keeps them from destroying each other's work is a boundary drawn before either of them runs.

The pipeline

deterministic — scripts, reproducible model-driven — needs a gate

The boundary that makes it survivable

Codegen runs again every time the user moves a button. If it writes to the same files the agent edits, the second generation destroys the first implementation. This is the failure that kills visual-builder products, and it is a file-layout decision, not a merge algorithm.

If you skip this: the second [Generate] silently erases every line the agent wrote. Users will not report it as data loss — they will report that the product "randomly forgets things", and you will be debugging a merge engine instead of building the platform.

What the gate can actually assert

"Validation" is doing a lot of work in the pitch. The word covers four different checks with wildly different cost and strength, and which one you mean changes the architecture.

CheckCatchesCostWeakness
Compiles Broken syntax, wrong types, bad references Seconds A stub that returns null compiles fine
Contract conformance Agent dropped or renamed something the design declares Milliseconds Only checks structure, never behaviour
Tests pass Behaviour, where a test exists Minutes If the agent writes the tests, it writes passing ones
Render matches design The thing the user actually asked for High — needs a device or Wasm build Hardest to build; flaky on font and timing differences

Contract conformance is the underrated one. It is nearly free, it is deterministic, and it is the only check in the list that directly encodes the design is the source of truth — the agent is not permitted to quietly disagree with the contract. Start there and at "compiles", and add the expensive checks per-step only where a step warrants them.

Sequencing, and why it is per-step

One generation that rewrites twelve files either works or leaves you with no idea which part broke. Splitting the diff into ordered steps — each one small enough that a gate failure points at a single cause — is what makes the loop recoverable rather than a coin flip.

  • Order by dependency, not by file. Types before the code that uses them, or every early step fails for the same downstream reason
  • Halt, don't skip. A step that fails its gate blocks the ones behind it; skipping ahead produces a half-built screen that compiles and lies
  • Bound the retries. Two attempts, then surface it to the user with the gate output. An agent looping on the same failure burns budget and changes nothing
  • Keep steps reversible. One commit per passed step means a bad run is a git reset, not an archaeology project

The open question

Everything above assumes the contract can express the design. It cannot express all of it — the moment a user wants a list that filters as you type, the design tool is describing behaviour, and behaviour is exactly what the contract was supposed to hand to the agent.

So the real design question is not the pipeline. It is where you draw the line between what the contract declares and what the prompt describes, and how a user expresses the second one inside a visual editor. Answer that and the rest is the engineering sketched here.
